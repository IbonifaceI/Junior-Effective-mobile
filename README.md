1. Структура базы данных (PostgreSQL)
В основе системы управления доступом лежат четыре ключевые таблицы. Именно они отвечают за то, кто и что может делать в приложении.

users_user: здесь хранятся основные данные о пользователях — ФИО, электронная почта, хеш пароля и статус активности.
users_role: это справочник ролей. В нём перечислены все возможные статусы, например: admin, manager, user, guest.
users_businesselement: справочник объектов приложения, к которым может потребоваться доступ. Типичные примеры: users, orders, products, access_rules.
users_accessrule: таблица связей. Она определяет, какие именно действия разрешены конкретной роли для конкретного объекта.

2. Принцип работы ролей и прав доступа
Проверка прав доступа происходит не на уровне базы данных, а в коде приложения — на уровне бизнес-логики (в View).

Привязка: каждому пользователю присваивается роль через поле role_id.
Правила: для каждой роли в таблице AccessRule прописаны свои разрешения.
Типы прав:
read_permission: можно ли просматривать записи.
create_permission: можно ли создавать новые записи.
update_permission: можно ли редактировать существующие.
delete_permission: можно ли удалять.
_all_permission: суффикс, который даёт доступ ко всем записям объекта (например, админ видит всех пользователей). Если его нет, доступ обычно ограничен только записями, созданными самим пользователем (через поле owner).

3. Примеры тестовых данных (для демонстрации)
Чтобы система заработала, нужно создать базовые роли и правила. Это можно сделать через удобный Django Admin или с помощью SQL-скрипта.

Роли:

Админ (admin): полный контроль над всеми объектами.
Менеджер (manager): может просматривать пользователей и товары, но удалять их не вправе.
Пользователь (user): работает только со своими данными и заказами.
Пример заполнения таблицы AccessRule:

Роль	Объект	Чтение	Создание	Редактирование	Удаление
Админ	Пользователи	✅	✅	✅	✅
Админ	Правила доступа	✅	✅	✅	✅
Менеджер	Пользователи	✅	❌	❌	❌
Пользователь	Заказы	✅ (только свои)	✅	✅ (только свои)	✅ (только свои)

4. Использование API
Для аутентификации система использует JWT-токены. Сессии здесь не применяются — только токены.

Регистрация пользователя
Метод: POST.
URL: /api/register/.
Тело запроса (JSON):
json
Копировать
{
    "first_name": "Иван",
    "last_name": "Иванов",
    "email": "test@example.com",
    "password": "StrongP@ss123"
}
Вход в систему (Получение токена)
Метод: POST.
URL: /api/login/.
Тело запроса (JSON):
json
Копировать
{
    "email": "test@example.com",
    "password": "StrongP@ss123"
}
Ответ: если всё верно, вернётся JSON с ключом token.
Авторизация запросов
Чтобы получить доступ к защищённым ресурсам, нужно передавать токен в заголовке каждого запроса:Authorization: Bearer <ваш_токен>

5. Примеры ошибок
Система использует стандартные коды HTTP для разграничения прав.

401 Unauthorized (Не авторизован):
Возникает, если в запросе нет заголовка Authorization или токен недействителен/просрочен.
Действие: нужно пройти процедуру входа (/api/login/).
403 Forbidden (Запрещено):
Возникает, если пользователь авторизован (токен верный), но у его роли нет прав на это действие.
Пример: обычный пользователь пытается удалить другого пользователя или посмотреть все заказы в системе.

6. Управление правилами доступа администратором
Администратор полностью управляет матрицей доступа через панель администратора Django (/admin/).

Что может делать Админ:

Создавать новые роли (users_role).
Добавлять новые объекты доступа (users_businesselement).
Детально настраивать права в таблице users_accessrule.
Назначать роли существующим пользователям.
Это позволяет гибко настраивать систему под нужды бизнеса без необходимости лезть в исходный код приложения.
